# 8. FAQ

Doubts that come up operating Spark here and that would not fit on previous pages. Esoteric errors are most of them, and the summary of all is the same: **almost everything that looks like a data problem is lack of memory**. If something is missing, open a PR adding it.

## Esoteric errors

### `java.lang.OutOfMemoryError: Java heap space`

Spark runs on JVM, and the JVM has an internal limit for operation memory. This memory is not the executor's (`spark.executor.memory`) nor the driver's: it is the JVM's own operation memory. "Heap space" usually means Spark tried to process at once more data than the JVM can handle.

The exit is **increasing the number of partitions**, via one of these paths:

1. **More threads/cores** — more partitions processed in parallel, each smaller ([session sizing](07-sessionsizing.md#threads-are-not-cores)).
2. **Reduce the partition size created from the physical file**, via `spark.conf`.
3. **Increase post-shuffle partitions**, if the overflow happens after a shuffle, with `spark.sql.shuffle.partitions`. Remember the default of 200 is **high** for any data below the billions of rows — in both directions: 200 tiny partitions cost more than they yield.
4. **Reduce the DataFrame's lateral size** — number of columns and value sizes. It is worth checking there is no wrong value in the middle, like a giant string in a single row.

Much more common in `local` mode with a small session.

### `Java gateway process exited before sending the driver its port number`

Appears when starting the `SparkSession`: configuration broke the JVM before the driver came up. Two causes cover almost all cases:

1. **No resource to start the JVM.** In `local` mode this happens with `spark.driver.memory` below 1 GB. Do not use Spark with less than 2 GB; comfortable is 4 GB.
2. **Jar conflict at startup.** When adding a new `.jar`, via Dockerfile or `spark.conf`, check compatibility with the Spark version and with Scala (the language Spark is written in). The image used here is `apache/spark:4.2.0-scala2.13-java25-python3-ubuntu`, that is **Spark 4.x with Scala 2.13** — a jar published for Scala 2.12 does not work.

### `py4j.protocol.Py4JNetworkError: Answer from Java side is empty`

The driver's JVM ran out of memory during execution (almost always) and broke, and the driver can no longer talk to it.

In Airflow, the fix is to increase memory in **both** places: pod `request` and `spark.driver.memory` — [they go together](07-sessionsizing.md#how-to-ask-exact-memory-overallocated-cpu), and raising only one does not solve it. In a notebook, it is raising the pod limit in the environment controller, respecting who shares the cluster and the end-of-month bill.

If memory volume seems enough and the error persists, the problem is in the process: see [where to look for memory bottlenecks](#where-to-look-for-memory-bottlenecks).

### `Required field 'uncompressed_page_size' was not found in serialized data!`

This is really esoteric. It looks like a data structure problem, and in most cases it is lack of memory: the JVM could not load a very large file in the defined number of partitions — a single 1 GB parquet falling into 2 or 3 partitions, for example.

The cruel detail is **when** it happens: at load time, which is lazy and only shows up at an action like `write`. There is no code operation that solves it, `repartition` included. Alternatives:

1. **Brute force:** more threads (cores) and more memory on the session.
2. **More partitions on read.** The default is the number of threads (parallelism); it can be raised with `spark.sql.files.minPartitionNum`.
3. **Smaller file at the source.** Usually the least viable, but the one that attacks the cause. If the source was written with Spark, there is probably a `df.repartition(1)` or `df.coalesce(1)` before the write. If you cannot touch it, Spark reads several files from the same folder with wildcard: `spark.read.format("parquet").load("/path/my_table/*.parquet")`.

## Where to look for memory bottlenecks

When memory seems enough and the job breaks the same way, the target is the code — bottleneck or unnecessary cache:

1. **Careful with Spark inside a loop** (`for`/`while`). Almost always it is more performative to do that inside Spark, with `window`, `join` and the like. It is not Pandas, where data is already in memory.
2. **Check duplicates generated by join.** Two non-unique keys generate one row per combination, and that multiplies — a lot — the DataFrame size. In development, confirm with `df.count()`; in production, ensure data quality before the join, not after.
3. **Remove unnecessary columns and rows before anything.** If only the current year matters, filter the date before anything else; if the number of columns is large and most will not be used, do `select` at the start.
4. **Careful with `dropDuplicates`.** Without argument it compares all columns and does a full table shuffle — not only non-performant, but dangerous: a duplicate row with a different timestamp survives and you keep the wrong one. Use `subset` with the columns of interest, and do not call it "just in case".
